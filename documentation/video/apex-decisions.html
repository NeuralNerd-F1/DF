01

The representation decision — engineered features over learned ones

The most consequential choice in the project happens before any library is imported: what is a "driver" to the system? APEX answers: a vector of 28 engineered behavioural features per lap, aggregated into a fingerprint — not a learned embedding from raw telemetry.

Behavioural feature engineeringchosen over end-to-end representation learning

Why this

  • Data regime. Four seasons of one series yields ~54,000 usable laps for 13 classes. That is small data by deep-learning standards; it is exactly the regime where engineered features plus gradient-boosted trees remain state of the art on tabular problems.
  • Every downstream promise depends on it. Exact SHAP attribution, plain-English signals in the UI, the monitor's exact per-feature alert attribution, and the setup engine's named basis features all require features with names and units. A latent embedding surrenders all four at once.
  • Failure semantics. An engineered feature can be range-checked (every feature has a documented valid range; violations go NULL with a code). A latent dimension cannot fail loudly, which collides with the project's first principle.
  • The public feed is weak. A boolean brake channel and ≈7.5 Hz true sampling cannot feed a high-frequency sequence model with real information — the data would not reward the architecture.

Alternatives considered

  • CNN/LSTM/transformer over raw traces — rejected for the data regime, explainability loss, and reproducibility cost (GPU nondeterminism, seed fragility). Recorded as the credible future architecture, in hybrid form: 28 engineered features + a learned latent block.
  • Hand-picked classical statistics only (mean speed, lap time) — rejected as too coarse: lap time is dominated by car and circuit, precisely the variance the project must see through.

If challenged ("why not deep learning?"): the honest answer is the data, not fashion — 54k rows / 13 classes / 7.5 Hz boolean brake. The architecture that wins on that corpus is the one chosen; the review's temporal-encoder proposal is the same funnel with a learned core, and the contracts, gates and serving layer would survive that swap unchanged.

02

Data sourcing and caching

FastF1 as the primary sourcechosen over OpenF1-only, scraping, or paid feeds

Why this

  • The only free source exposing per-sample car telemetry (speed, throttle, brake, RPM, gear) with lap and session context, wrapped in a maintained Python API with its own local cache.
  • Session metadata (track status, pit in/out) arrives aligned with telemetry — the validation filters need both in one place.

Alternatives considered

  • OpenF1 — kept as a fallback for tyre/lap context; its telemetry coverage and history are thinner across the 2022–2025 window.
  • Ergast — results and metadata only, no telemetry; retained as a second fallback for lap context.
  • Paid/team data — out of budget and out of licence for an academic project; also would weaken the "public data only" claim that scopes the findings.

If challenged ("is the feed good enough?"): that question is a finding — the boolean brake channel and 7.5 Hz rate are stated limitations, and the results are explicitly claims about what public telemetry supports.

Parquet telemetry cache at raw sample ratechosen over CSV/JSON files or a database

Why this

  • Columnar, compressed, typed — a season of telemetry reads in seconds and the 53,928-vector matrix builds in a single pass.
  • Cached at raw rate deliberately: the resampling policy stays a downstream, changeable decision instead of being baked into the download.

Alternatives

  • CSV/JSON — no types, 5–10× the size, slow scans.
  • Loading telemetry into Postgres — the database is for serving entities (drivers, fingerprints, predictions), not hundred-million-row sample data; bulk columnar analytics is Parquet's home ground.
Circuit breakers + stale-cache serving on every external callchosen over naive retry loops

Why this

Each source has a policy (timeout, bounded retries with backoff, breaker opening after repeated faults in a window). When a source is down, ingestion serves from the local cache tagged STALE_DATA — degraded and saying so, which is principle 1 applied to the network. Naive retries hang pipelines and hammer APIs; silent fallbacks hide outages. The specific constants (5 s timeout, 3 retries, doubling backoff, breaker at 3 faults/30 s) are conventional operational values fixed a priori — nothing downstream is sensitive to them, so tuning them would have been fake precision.

Validation and its thresholds

Nine filters sit between raw laps and the feature extractor. The design position: a behavioural baseline must be built only from laps where the driver was actually expressing normal racing behaviour — and every exclusion must be counted, coded and reportable.

ThresholdValueWhy this value, not another
Green-flag onlyLAP_001Safety cars and red flags produce pace-managed driving — real behaviour, wrong distribution. Keeping them would poison every baseline with a second mode.
No out/in-lapsLAP_002Pit-entry and warm-up laps are procedural, not racing; they are also trivially separable, so excluding them is cheap and clean.
Sample-rate floor20 HzThe distinguishing behaviours live in 100–300 ms transitions; resolving a transition needs several samples inside it. At 20 Hz a 150 ms ramp spans 3 samples; at 5 Hz it is one step. The public feed is resampled to 50 Hz to clear this floor mechanically — stated as adding no information.
Lap-time bound115% of driver medianModelled on the sport's own 107% rule but looser on purpose: 110% laps are usually traffic or tyre management — genuine behaviour worth keeping; beyond 115% it is damage or cool-down.

Stationary check>1% stationary → rejectCatches spins, stoppages, and data glitches that lap-time filters miss.

If challenged ("aren't these thresholds arbitrary?"): each has a stated mechanism (above), they were fixed in the specification before the real corpus was seen, and the corpus reports what they cost — 84% acceptance, with the loss broken down by code. Sensitivity to the marginal choices is small because the dominant exclusions (green flag, pit laps) are categorical, not threshold-tuned.

04

The 28 features

Twenty-eight features across six behavioural domains — throttle, braking, speed, gear, engine, cornering — plus consistency, corner-balance and tyre-age drift terms. The design intent: each feature is a named, unit-bearing, range-checked claim about driving behaviour, cheap to compute from the available channels, and robust to the feed's limitations.

What the features measuretransitions and distributions, not raw magnitudes

Representative members: full-throttle share and lift frequency (commitment vs modulation); mean of the top-N brake-pressure peaks and braking-event counts (attack vs conservation on a boolean-derived channel); speed percentiles p10/p90 (how slow the driver is willing to go, how fast they dare); redline share and gear-change counts; brake→throttle transition rate and brake-throttle overlap (footwork); lateral-G means and peaks with steering-correction rate from the position channels (cornering commitment and tidiness); corner-entry balance; per-stint drift slopes of throttle and braking against tyre age (F27/F28, the monitor's slope component).

Why distributions and transitions

Raw magnitudes (top speed, lap time) are car-and-circuit properties. The behavioural signal lives in how a driver moves between states — ramp shapes, overlaps, percentile spreads — which survive car changes far better and are what the season-drift evidence later validates.

Alternatives

  • Fewer, coarser features — the ablation answers this empirically: every single domain alone scores far below the full 28; discrimination is spread.
  • Hundreds of auto-generated features (tsfresh-style) — rejected: uninterpretable members would break the explanation contract, and the multiplicity invites overfitting the tuner instead of the problem.

The NULL contract

A feature that cannot be computed honestly (too few braking events, unknown tyre age, missing position data) is NULL with a code, never a guessed value; a computed value outside its documented range raises internally and lands as NULL + FEATURE_001. Vector assembly tolerates six NULLs (~21%) via train-median imputation, each tagged; the seventh rejects the lap — beyond that point the vector is more imputation than measurement, and imputation pulls every driver toward the population median, erasing exactly the individuality the classifier needs.

If challenged ("why 28, exactly?"): the count is not sacred — it is the set of behaviours the channels can support honestly, fixed in the specification. The defensible part is the process: named semantics, valid ranges, coded failure, and an ablation that measures what each domain contributes.

05

Normalisation and the leakage architecture

Per-circuit z-scoring of six circuit-sensitive featurestrain-only fit, single-writer/two-reader

Why the architecture is shaped this way

  • One writer. fit_normaliser is the only function in the codebase that computes normalisation statistics. It excludes the held-out circuits and the non-train split before any aggregation, then a fail-loud tripwire re-checks and raises if a quarantined circuit somehow survived — no artefact is written on a poisoned run.
  • Two readers. Loading validates a content hash (corrupt or stale params raise); applying is a pure transform that never fits and never raises — an unknown circuit falls back to global parameters with a logged NORMALISATION_FALLBACK.
  • Why only six features: the circuit-dependent ones (corner speeds, lateral-G levels). Z-scoring everything would have destroyed unit semantics for features that are already circuit-stable.

Alternatives

  • Global normalisation only — the original argument against it was that circuit character would masquerade as driver style. See the inversion below for how the evidence adjudicated this.
  • Fitting scalers per split at use time — the classic leakage bug; architecturally impossible here by the single-writer design.

The inversion — the project's best finding, and how it was handled

The evaluation ablation showed that training the identical model on raw features lifts held-out macro-F1 from 0.413 to 0.614. Belgium and Italy were never trained on, so this cannot be circuit-identity leakage: the raw levels of the six circuit-sensitive features carry driver-discriminative signal that per-circuit z-scoring erases — drivers differ in how fast they are willing to go, and a per-circuit z-score subtracts much of that. The zero-shot fallback mismatch accounts for only ~3 points (measured by a paired calibration protocol), so the erasure, not the fallback, is the cost.

The decision discipline matters as much as the finding: the classifier — alone — was re-scoped to raw features via a config-recorded flag; its Optuna study re-ran from scratch; the champion bundle records its representation and serving obeys the bundle; and every other model (style space, monitor, setup) keeps the leakage-guarded normalised pipeline, because their jobs (cross-circuit geometry, within-stint deviation) still want circuit effects removed. Nothing was patched in place; the evidence, the decision and the artefacts are all recorded.

If challenged ("doesn't raw representation leak circuit identity into the classifier?"): the held-out design answers it — the test circuits were never trained on, so the classifier cannot have memorised them; what raw features carry is driver-level willingness/commitment signal that generalises across circuits, which is precisely what the held-out lift demonstrates.

06

The identification stack

XGBoost (gradient-boosted trees)chosen over RF, linear models, SVM, kNN, deep nets

Why this

  • The regime. 28 engineered features × 54k rows is the tabular mid-size regime where boosted trees remain state of the art.
  • Native NaN handling. Trees route missing values through learned default directions — which composes exactly with the tolerated-NULL contract: no second imputation model at serve time.
  • Exact explainability. TreeExplainer computes exact SHAP values on tree ensembles in polynomial time — the whole explanation layer rides on this.
  • Calibratable probabilities. Boosted margins calibrate well under isotonic regression, which the confidence gate requires to mean anything.

Alternatives, and the specific reason each lost

  • Random forest — kept as a baseline (0.375 vs the champion's like-for-like 0.407): weaker probability calibration and no exact SHAP; both load-bearing.
  • Logistic regression — baseline (0.245): the boundaries between driving styles are not linear in these features.
  • SVM — poor probability semantics (Platt bolted on), O(n²) kernels at 54k rows, no missing-value story.
  • kNN — distance in 28 mixed-unit dimensions is exactly the trap the style space needed a scaler for; no calibrated confidence; serving cost grows with the corpus.
  • Deep nets — §1's representation argument, plus reproducibility cost.

If challenged ("did you try X?"): RF, logistic and majority baselines are in the training summary; the deeper alternatives are rejected on stated structural grounds (data regime, explainability contract), not on a missing benchmark — and the design record marks a hybrid learned representation as the credible successor.

Optuna (TPE) hyperparameter search, 200-trial floor, resumable SQLite storagechosen over grid/random search

Why this

  • The tuned space (depth, learning rate, subsampling, regularisation, estimator count) is ~8-dimensional; grid search is either coarse or combinatorially absurd there, and TPE-style samplers reliably beat random search at equal budget.
  • Resumable storage was a hard requirement, not a nicety: the real study cost ~11 hours (~3.3 min/trial); a crash resumes mid-study instead of restarting. The sampler is seeded, so the study is reproducible.
  • The study key hashes the fit data — so when the representation changed (§5), a fresh study was forced by construction, not by remembering to delete a file.

Alternatives

  • Grid search — dimensionality; random search — no resumption/pruning story at this budget; defaults — indefensible when the headline number is the dissertation's core claim.
StratifiedGroupKFold grouped by circuitchosen over lap-level K-fold

Why this

With lap-level splitting, the same circuit appears on both sides of a fold, and the model scores partly by recognising circuit context — the leakage that flatters most published driver-classification numbers. Grouping by circuit puts each circuit wholly inside one fold: the CV objective then measures the thing actually claimed — generalisation across circuits. Stratification keeps the 13 classes balanced per fold. This deliberately costs headline score and buys validity; the cost is visible in the CV-vs-held-out comparison and stated, not hidden.

If challenged ("your CV number is lower than papers X/Y"): that is the point — those numbers are typically lap-level CV, which this design classifies as leaked. Like-for-like, APEX's held-out protocol is stricter than most published evaluations in this niche.

07

Calibration and the gates

Isotonic calibration on a disjoint 20% splitchosen over Platt scaling or raw probabilities

Why this

  • The gate is only meaningful if "0.65" means what it says: an uncalibrated max-prob of 0.65 can correspond to a 40% or a 90% empirical hit rate.
  • Isotonic over Platt: Platt assumes a sigmoid-shaped miscalibration; isotonic is non-parametric — it assumes only monotonicity — and with tens of thousands of calibration points it has the data it needs. Boosted-tree miscalibration is not reliably sigmoid.
  • The calibration split is disjoint from every training fold, so the calibrator never sees data the booster trained on. (Mechanically: scikit-learn ≥1.6 removed cv="prefit", so the fitted booster is wrapped in FrozenEstimator — a recorded stack decision.)
The gate: entropy > 2.9 bits → AMBIGUOUS, else max-prob < 0.65 → LOW_CONFIDENCEtwo gates, entropy first

Why two gates, and why entropy takes precedence

  • Max-prob alone cannot distinguish "no idea" from "torn between two": a 0.45/0.45 split and a flat 13-way smear both fail the 0.65 test, but they are different epistemic states deserving different words. Shannon entropy over the full calibrated distribution captures the smear; it is checked first because a flat distribution makes the max-prob number meaningless anyway.
  • Why 0.65: fixed a priori. For 13 classes it demands ~8.5× the chance probability mass before the system names a driver; post-calibration it reads as "right about two times in three" as the minimum standard for a named answer. The held-out measurement then validated the design: 74.8% accuracy-when-answering at 71.9% coverage.
  • Why 2.9 bits: log₂(13) ≈ 3.70 bits is a uniform smear; 2.9 sits far enough below to permit genuine multi-way uncertainty yet still refuse near-uniform distributions.

Alternatives

  • No gate (always answer) — 63.6% top-1 with silent failures; the gate converts a mediocre forced-choice classifier into a trustworthy selective one.
  • Reject-option learning / conformal prediction — conformal sets are the sophisticated cousin; rejected for this build because the typed-state UX (a named driver or an explicit refusal) is the product contract, and calibrated max-prob + entropy delivers it with two auditable thresholds. Noted as future work territory.

If challenged ("the gate values are magic numbers"): they live in config.yaml, were set a priori with stated rationales, and the serving metrics measure exactly what they buy. The system never re-derives them anywhere — the UI reads the served state.

Propagated confidence = feature-quality × distribution × model-confidencemultiplicative, zero new thresholds

Why this composition

Each factor is a distance from a boundary the system already enforces (the NULL ceiling, the entropy gate, the calibrated max-prob). Multiplying means one weak link drags the composite down — a conjunctive reading of trust — and introduces no arbitrary weights to defend. It is deliberately presentational: computed after the gate from the gate's own inputs, explaining the verdict without ever overriding it. An additive weighted score was rejected precisely because the weights would have been three new indefensible constants.

08

Explainability

SHAP TreeExplainer, exact, over the champion's base boosterchosen over KernelSHAP, LIME, permutation importance

Why this

  • Exactness. TreeExplainer computes exact Shapley values on tree ensembles — no sampling variance, reproducible to the digit, and cheap enough to run inline per prediction (~43 ms including the model call).
  • Additivity is auditable. The attributions sum to the model margin; a consistency check flags any mismatch (SHAP_CONSISTENCY_WARN) rather than trusting the library blindly.
  • Explaining the base booster, not the calibrated wrapper: isotonic calibration is a monotone map, so the base margins carry the decision structure; TreeExplainer needs the tree model.

Alternatives

  • KernelSHAP / LIME — sampling approximations: slow, noisy, and nondeterministic; every property the project's contracts forbid.
  • Permutation/gain importance — global only; the product needs per-prediction, signed, per-class attribution.

The degradation rule

Explainability never blocks a prediction: a SHAP fault degrades to SHAP_UNAVAILABLE and the prediction serves without it. An explanation is an enhancement of an answer, not a precondition — but a fabricated explanation would be worse than none, so absence is typed and rendered honestly.

The style space

56-dim aggregate (mean + spread of all 28 features)chosen over lap-level embedding or sequence models

Why this

A driver's style is a distribution, not a lap: the mean says where they sit, the spread says how variable they are — consistency is itself a style trait. The aggregate is stable (thousands of laps per driver), interpretable (each of the 56 dims has a name), and small enough for honest small-sample dimensionality reduction. Sequence information is deliberately discarded and stated as the known cost — the review's temporal-embedding critique is accepted as future work.

The aggregate scaler — a caught bug worth telling

The 56 dims mix unit-scale fractions with physical units spanning four orders of magnitude; Euclidean UMAP on that would have measured unit scale, not style. A train-only standardiser now sits inside the leakage guard — caught in review, recorded as a numbered divergence, and a good faith-in-process exhibit.

UMAP → 5D fingerprint + 2D view, with a persisted PCA fallbackchosen over t-SNE or PCA alone

Why this

  • UMAP over PCA: neighbourhoods are the product — "who drives like whom" — and UMAP preserves local neighbourhood structure through non-linear relationships PCA flattens.
  • UMAP over t-SNE: t-SNE has no transform for new points, and projecting a new aggregate through the frozen model — a forward pass, never a refit — is required in three places: the season-stability measurement (each season's aggregate projected through one frozen model, which is RQ3's evidence), the out-of-distribution gate below, and the retained POST /fingerprint/unknown endpoint. t-SNE would have to re-embed the world per query, which makes coordinates incomparable between runs — fatal for a stability claim.
  • The PCA fallback: UMAP on 13 points is fragile and version-sensitive, so a deterministic PCA projection is trained and persisted alongside it. If UMAP cannot serve, the surface degrades to PCA and says so — honest degradation, not a crash. The PCA basis doubles as the out-of-distribution yardstick: a projected aggregate beyond 3σ on any principal component returns OUT_OF_DISTRIBUTION instead of a confident placement.
  • Small-sample honesty: n=13 is stated, stability is measured (repeated seeded runs, Procrustes-aligned variance), and the claims lean on the statistics that survive small n — the permutation test (p = 0.024) and nearest-neighbour rates — not on the picture.

If challenged ("UMAP on 13 points is meaningless"): agreed in the naive reading — which is why every claim is a permutation-tested statistic on the 56-dim space or a measured rate, the 2D view is presentation, the fallback is deterministic, and sparsity/OOD gates guard projection.

The behavioural deviation monitor

A calibrated statistical detectorchosen over a learned degradation model

Why not learned

There are no labelled degradation events to learn from — stint end (pit stop or flag) is the only observable and is itself a proxy. A supervised model would learn the proxy's noise and could not explain its alerts. A statistical detector against the driver's own baseline is defensible, explainable, and its false-positive rate is derivable rather than estimated.

Cosine distance on standardised featureschosen over Euclidean, Mahalanobis, DTW

The three-way comparison

  • Euclidean conflates magnitude with shape: fuel burn and track evolution move every feature's magnitude lap by lap, which would read as constant "degradation".
  • Mahalanobis whitens by a covariance the data cannot support — a 26×26 covariance estimated per 30-lap cell is singular or wildly unstable.
  • DTW / sequence distances — the vectors are per-lap summaries, not time series within the comparison; alignment has nothing to align.
  • Cosine on standardised features isolates exactly the quantity of interest — has the shape of the behaviour rotated away from the driver's own baseline — and is scale-free by construction.

The exact attribution

Because the vectors are unit-normalised, 1 − cos = ½‖x̂ − b̂‖² — so the per-feature terms ½(x̂ᵢ − b̂ᵢ)² sum to the distance exactly. The alert banner's feature chips are those terms, not a post-hoc estimate; a test asserts the sum to float tolerance.

τ = μ + 2σ per driver per circuit type · 3-lap baseline · 3-lap rolling mean · 2-crossing confirmationevery constant with a mechanism

Why these values

  • 2σ: under approximate normality, ≈2% one-sided false-positive rate per lap — squared by the two-consecutive-lap confirmation to well under one false alert per thousand scored laps. σ comes from the same per-cell calibration as μ, so an erratic driver-circuit pairing earns a proportionally wider band instead of an alert storm.
  • First-3-clean-laps baseline: the freshest honest picture of "this driver, this stint, healthy tyres"; extended to a 5-lap window when the first three aren't clean — coded, not silent.
  • 3-lap rolling mean: one lap of smoothing kills single-lap noise (traffic, one mistake) at the cost of one lap of latency — the cheapest possible trade at race timescales.
  • One crossing = WATCH, two = ALERT: escalation by persistence, not by hue — a single excursion is information, a sustained one is an event.
  • Per driver × circuit type calibration cells (street / high-speed / technical / mixed): per-circuit cells would starve on data; global cells would flag naturally erratic pairings constantly. Cells with fewer than three training stints are marked unusable rather than served thin.

If challenged ("91% of alerts self-resolve — isn't the detector just noisy?"): the claim was renamed to match the evidence — this is behavioural deviation monitoring, transients included; degradation is one driver of it, and the pit-stop proxy bounds what stronger labels could say. The false-positive mechanism is derivable; what's proxy-bounded is the semantic label on true events.

Setup tendencies — the exploratory extension

Three layers: learned mapping → FIA constraints → per-parameter reliabilitywith transparent heuristic targets

Why heuristic targets, stated everywhere

No public ground-truth setup data exists — teams do not publish wing angles. The training targets are transparent, monotonic maps of named fingerprint features, deliberately without fitted constants, so the learning is confined to the fingerprint→setup mapping and the compounding uncertainty is explicit. The output language follows: "telemetry-derived setup tendencies associated with the fingerprint — heuristic targets, not ground-truth setups", a mandatory disclaimer field, and direction-vs-grid phrasing instead of engineering point values.

Why the three layers

  • Mapping: one XGBoost regressor per parameter over the 5D fingerprint + circuit-type one-hot (drop-first — 4 types, 3 dummies, no dummy trap) — same library rationale as §6, same explainability dividend.
  • Constraints: FIA legal ranges clip every output; a Monaco-style maximum-downforce override and consistency flags catch physically incoherent combinations — domain rules enforced in code, not left to the model.
  • Reliability: per-parameter confidence = 1 − cross-validated normalised error, attenuated for out-of-distribution fingerprints; below the 0.5 floor the system returns a range, not a point. The evaluation's best result validates this layer specifically: served reliability correlates with held-out error at r = −0.80 — when the system says trust me less, it is measurably less trustworthy.

If challenged ("this can't be validated"): correct as stated, which is why it is presented as an exploratory extension with internal-consistency evidence (direction agreement 0.68/0.77 across seasons and contexts, smooth perturbation responses, the r = −0.80 reliability tracking) — association, never causal validation, and roughly five of ten parameters reliably inferrable, reported not narrowed.

Corner decomposition — an ablation instrument

Slow / medium / high-speed corners by apex radius, five sub-features eachbuilt to answer a question, not to inflate a number

Why apex radius

Corner type is defined by geometry, not speed: radius r = 1/κ at the apex, computed from the position channels' curvature — reusing the same curvature primitive the lateral-G features use, so there is one geometry implementation to trust. Radius thresholds (100 m / 200 m) follow racing convention for slow/medium/fast classification.

Why it exists

Its deliverable is the ablation question — does corner-type information improve identification? — where a neutral result is a legitimate finding. Laps without usable position data skip decomposition with a code and continue; the sub-fingerprint cells require a minimum corner count before they claim anything.

13

Backend engineering

Python 3.12+ · pandas 3 · numpy 2a wheel-driven, ratified migration chain

Why the stack sits where it does

The floor moved during the build because binary wheels for the pinned scientific stack demanded it, and each transitive move was ratified and recorded rather than absorbed: numpy's modern line requires Python ≥3.12; full MLflow caps pandas below 3, so the project uses mlflow-skinny (same tracking API) on a SQLite-backed store; SHAP's numba dependency pulled numpy back one minor version — re-running the full suite green before any new code; and asyncpg ships no wheel for the pinned Python, so the Postgres driver is psycopg v3. The meta-decision is the defensible part: dependency reality is a design force, and every migration has a written cause the code can be traced back to.

FastAPI + Pydantic v2chosen over Flask or Django

Why this

  • Typed contracts as the framework's native language. Every pipeline stage already returns a Pydantic result object; FastAPI serves those same models as validated DTOs and generates the OpenAPI schema the frontend's typed client is built from — one type system from feature extractor to browser.
  • Async serving composes with the async persistence layer.
  • The application factory has a best-effort lifespan: a model handle that fails to load degrades to None with a logged reason and /health reports exactly what is unready — serving degraded beats not serving.

Alternatives

  • Flask — no native validation/schema story; every DTO contract would be hand-rolled middleware.
  • Django — an admin-and-ORM monolith for a typed inference API; heavy in exactly the dimensions this project doesn't use.
SQLAlchemy 2 async + Alembic · offline tests on aiosqliteportable persistence with real migrations

Why this

  • Async ORM matches the serving stack; Alembic gives migrations a history instead of drift.
  • Portable column types let the entire database suite run offline on SQLite — CI needs no server — while a marked test exercises the real Postgres migration when a DSN is present. The DSN itself is environment-only; config stores the variable's name (secret hygiene).
  • Database faults follow the same contract as everything else: a breaker, a typed DB_UNAVAILABLE, and a no-partial-write guarantee exercised by the fault harness.
The failure contract: 69-code enum · typed results · append-only DQ logchosen over exceptions-as-control-flow or ad-hoc logging

Why this shape

  • Enum, not strings: a typo'd error string is a silent failure of the failure system; an enum member is checkable, greppable, and each member has a test that triggers it.
  • Results, not exceptions: pipeline stages return typed result objects with status + code; predict() never raises. Exceptions are reserved for genuine invariant violations (the leakage tripwire) where crashing loudly is the correct behaviour.
  • Append-only JSONL data-quality log: every dropped lap, fallback and refusal is one auditable row; the API serves tallies from it, so the UI can say "6,809 laps rejected: not green-flag" with a straight face.
config.yaml as the single source of every constantno magic numbers, typed on load

Why this

Every threshold, seed and path lives in one annotated file, loaded through typed Pydantic config models (extra forbidden — an unknown key is an error, not a silent ignore). Blocks reference shared values rather than re-declaring them, so "the gate" exists exactly once. The payoff is auditability — an examiner pointing at any number on screen can be walked to its one definition and its rationale comment — and the inversion decision (§5) being one recorded flag instead of a code hunt.

mlflow-skinny on a SQLite storetracking + registry without the pandas cap

Why this

Every training run logs params, metrics and artefacts; the champion is a registered model, so "which model is serving" has an answer. Skinny because full MLflow's dependency set caps pandas below the project's line; a database-backed store because the registry does not support file stores. The champion bundle on disk (model + normalisation + labels + representation sidecar) is the serving seam — inference obeys the bundle, so training-time decisions cannot silently diverge from serving.

Testing: mirrored suites, failure-path fixtures, an executable fault harness1,354 tests as the enforcement mechanism

Why this shape

  • Tests mirror app/ one-to-one, so coverage gaps are visible in the tree itself.
  • Every error code has a triggering test — the failure contract is enforced, not aspirational; fixtures include synthetic failing laps by design.
  • The fault-injection harness is evaluation, not just testing: it assembles the real application, injects seven faults (ambiguous input, source outage → stale cache, the NULL boundary, a downed optional dependency over 100 consecutive predictions, database down with no partial write, an out-of-distribution projection, a raising explainer) and asserts coded, logged, served outcomes. RQ5's evidence is executable.
  • Browser-level e2e deferred — a stated gap: 243 component tests cover screen behaviour; Playwright would add integration confidence and is queued as future work rather than claimed.

Frontend engineering

Next.js 14 (App Router) + TypeScript strictchosen over a plain SPA, Streamlit, or Dash

Why this

  • The interface is a real product surface — six interactive screens behind five top-level tabs (a Driver Profile is reached by clicking an overview card, not by a tab of its own), with shared navigation and state — not a notebook veneer. The style space reaches the user as the 2D style map embedded in the Driver Profile; the standalone WebGL scatter lives on master, outside this build's presented surface. Streamlit/Dash trade exactly the control (layout, interaction, design tokens) this project's presentation quality depends on.
  • TypeScript strict + a generated client: the API's OpenAPI schema generates the client types, and zod validates every response at runtime — a backend rename fails loudly in tests, not silently in the browser.
  • The four-state result union (loading / empty / error / success) is principle 1 reaching the browser: every screen renders every state, and empty is distinguished from broken.
D3 + hand-built SVG chartschosen over chart libraries

Why this

The visualisations are bespoke instruments — shared-scale paired radars, signed SHAP force bars, a causal deviation timeline with a τ line, a fingerprint-drift trail. Chart libraries excel at standard charts and fight custom ones; D3 primitives plus deterministic SVG give exact control and testable output (deterministic rendering is asserted in tests). Radar axes scale to the grid maximum so shapes are comparable — the earlier rim-clamping bug is a recorded, fixed lesson.

Zustand for client state · Tailwind design tokenssmall tools for small jobs

Why this

  • Zustand over Redux: the only genuinely shared client state is playback (position, speed, play/pause across replay panels); a 3 KB store fits, a Redux architecture would be ceremony.
  • Design tokens in one Tailwind config: no colour or font literal in any component — enforced by a guard test that scans the source. The palette is semantic: assert rose when the model states something, epistemic purple when it declines, operational amber when it serves compromised — the UI's colours are readouts of served states, and no component re-derives a threshold to pick one.

Evaluation design

Held-out circuits (Belgium, Italy), fixed a priorichosen over random splits or post-hoc selection

Why this

  • Circuit-level holdout is the only split that tests the actual claim — generalisation to unseen circuits. Random lap-level splits answer an easier question nobody asked.
  • Fixed in the specification before any data was seen, which forecloses the accusation of picking a friendly test set. Both run in all four seasons with rich coverage, and they are different circuit characters — Spa's long high-speed sweeps, Monza's low-downforce braking zones — so the test spans two archetypes rather than one.
  • The quarantine is enforced in code (§5), not in discipline.
Five read-only studies plus harvested serving metricsevaluation that cannot contaminate what it measures

Why this shape

Five studies — the domain-shift A/B protocol (zero-shot vs calibration-laps-only normalisation, paired on identical scored sets, classifier frozen, persisted artefact hash-asserted untouched), the ablation matrix, the style-space statistics, the detector sweep, and the setup validation — plus the serving metrics harvested from the champion run, all execute read-only over the frozen served bundles, emitting six content-hashed JSON artefacts under artefacts/real/eval/. No .fit() in any evaluation path; deliberate eval-only computations (the B-protocol's in-memory circuit statistics) are labelled as such and tested disjoint. Every number in the dissertation, the video and this dossier resolves to one of those files.

If challenged ("could the evaluation have leaked into the model?"): the direction of information flow is one-way by construction — evaluation reads bundles and writes JSON; the one model change the evaluation motivated (the representation re-scope) went back through the full training path with a fresh study, not through a patch.

Targets kept when missedDEGRADED as a first-class, reported status

Why report a miss instead of rebasing the target

The 0.78 macro-F1 target was calibrated against a synthetic fixture before real data existed. When the real corpus landed at 0.6225, the honest moves were all taken: the run reports DEGRADED and writes the champion anyway; both numbers appear side by side everywhere; and the gap was investigated until it yielded the representation finding. A silently rebased target would have cost the project its most valuable result and its credibility in one move.

Reproducibility

Seeds fixed in config · single-threaded boosters · content-hashed, timestamp-free artefactsbyte-identical re-runs as the standard

Why each piece

  • Seeds in config (numpy, XGBoost, the Optuna sampler): one place, versioned, impossible to vary silently.
  • n_jobs=1 in XGBoost: parallel histogram building introduces nondeterministic floating-point reduction order; single-threaded training costs wall-clock and buys bit-identical models — the right trade for a dissertation whose numbers must be reproducible on demand.
  • Content-hashed, timestamp-free artefacts: two runs on the same inputs produce byte-identical files, so "did anything change?" is a hash comparison, and every artefact self-identifies. The champion bundle records its own representation and provenance; serving obeys the bundle.
  • MLflow run per training: parameters, metrics, and artefacts logged, so any number can be traced to the run that produced it.

If challenged ("can I reproduce your headline?"): yes — fixed seeds, resumable study storage, hashed artefacts and the recorded config make the 0.6225 a re-runnable claim, not a screenshot.

The meta-decision that ties the dossier together

Almost every choice above follows from three commitments made before any code: no silent failure, no leakage, and claims scoped to evidence. Tools were selected for how well they serve those commitments — exact SHAP over approximations, isotonic over assumed shapes, typed enums over strings, group-CV over flattering splits, a reported miss over a rebased target. When an examiner asks "why X?", the honest template answer is: because it kept a promise the system made elsewhere.
