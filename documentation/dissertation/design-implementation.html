Chapter 3

Design

This chapter presents the design of APEX: the principles fixed before any code was written, the layered architecture those principles produce, the design of each pipeline stage and model, and the considered alternatives that were rejected. The design is argued from its central representation outward — the driver behavioural fingerprint — and from one governing commitment: no component fails silently.

3.1Design context and goals

Two drivers in mechanically identical cars produce measurably different telemetry. APEX treats that difference as a behavioural signature. The system ingests public Formula 1 telemetry, reduces each accepted lap to a 28-feature behavioural vector, aggregates those vectors into a per-driver fingerprint, and then does four things with it: validates it (driver identification — if identity is not recoverable from the fingerprint, it carries no signal), gives it geometry (a continuous style space), explains it (exact SHAP attribution), and applies it downstream (behavioural deviation monitoring and setup-tendency estimation). Every research question in Chapter 1 is a question about this one representation, and the design is organised accordingly: the fingerprint is the core, identification is its validation, and the remaining capabilities are its applications.

Three properties of the problem shaped the design more than any other consideration. First, the data source is public and imperfect: the telemetry feed arrives at roughly 7.5 Hz with a boolean brake channel, so the design must state what the feed can and cannot support rather than assume laboratory-grade signals. Second, the central scientific claim — that the fingerprint generalises to circuits the system has never seen — is only testable if the evaluation circuits are quarantined from every fitting operation from the first line of code; leakage prevention is therefore an architectural concern, not an evaluation-time check. Third, the system serves model outputs to an interface, and a model output of unwarranted confidence is a worse failure than an honest refusal; uncertainty handling is consequently designed in as a first-class output type rather than added as presentation.

The design goals follow directly: (i) a single audited path from raw telemetry to the fingerprint, with every loss of data counted and attributed; (ii) models that abstain, with typed uncertainty states, rather than force answers; (iii) a train/held-out boundary that is mechanically enforced rather than promised; (iv) reproducibility to the byte for every trained artefact; and (v) an interface that renders what the system knows, including what it does not know.

3.2Design principles

Five constraints were fixed in the project specification before implementation began, and they are enforced mechanically — by types, tripwires, and tests — rather than by convention. They are stated once here; the rest of both chapters refers to them by number.

Principle 1 — No silent failure. Every failure path returns a typed result carrying an explicit error code. No bare except, no dropped lap, no swallowed fault.

Enforced by a 69-member ErrorCode enumeration, an append-only data_quality_log, and a read-only failure audit run against every module.

Principle 2 — No normalisation leakage. Scalers and statistics are fitted on the training split only, persisted as artefacts, and loaded read-only by everything downstream. The held-out circuits (Belgium and Italy) never touch a .fit() call.

Enforced by a single-writer/two-reader normalisation module and _assert_no_leakage tripwires at all four fit sites in the system.

Principle 3 — Reproducibility. All seeds are fixed in configuration; artefacts are content-hashed and timestamp-free, so re-running a build produces byte-identical output.

Enforced by seed 42 across numpy/XGBoost/Optuna, single-threaded training where parallelism breaks determinism, one MLflow run per training, and deterministic artefact hashing.

Principle 4 — Mandatory confidence gates. A model output below its confidence threshold returns a typed uncertainty state — LOW_CONFIDENCE, AMBIGUOUS, OUT_OF_DISTRIBUTION — never a forced answer.

Enforced by a calibrated gate at maximum probability < 0.65, entropy and distance gates on the other models, and an interface that colours by the served state and never re-derives a threshold.

Principle 5 — Failure paths are unit-tested. Every error code has a test that triggers it; a feature is not complete because its happy path works.

Enforced by 50 backend test modules mirroring the application tree, synthetic passing and failing fixtures, and a conformance check before any feature is accepted.

Corollary — Honest degradation. Where a component cannot deliver, it says so in the type system rather than substituting a plausible value. DEGRADED is a first-class status, and the interface renders explicit unavailable states rather than fabricating.

Principle 2 dominates the architecture. It makes normalisation a chokepoint that every downstream model must pass through, and it is the reason the classifier, style space, deviation detector, and setup engine each re-derive and re-assert the train/held-out boundary independently rather than trusting their caller: the redundancy is deliberate, so that a single filter bug cannot silently poison an artefact. Principle 4 supplies the system's most distinctive behaviour — the licence to abstain — whose quantitative payoff is measured in Chapter 5. Principles 1, 3, and 5 are what make the other two auditable.

3.3Architecture

The system is one funnel with typed boundaries. Telemetry becomes behavioural features; features become the fingerprint; everything else is either a validation of the fingerprint or an application of it. Figure 3.1 shows the architecture with its failure philosophy made explicit: the three path colours are the design in one picture.

success path failure path — typed error, logged, surfaced uncertainty state — “I don't know”, served, never forced

The amber and purple paths embody the design's central distinction. A data fault — a source outage, a malformed lap, an out-of-range feature — becomes a typed error with a logged reason that the interface shows verbatim. A model fault is not an error: it is a served uncertainty state (Principle 4). The answer “I don't know” travels the success path and is rendered in its own epistemic colour rather than disguised as a weak answer. This distinction recurs at every layer of the design and is the reason the system can miss a performance target and still be operating exactly as designed.

The alternative — one monolithic pipeline — was rejected because it makes failure isolation impossible: one exception tears down unrelated capability. Layers with typed result boundaries (ValidationResult, FeatureResult, PredictionResult, and their peers) let each stage fail alone, carry its reason, and leave the remainder serving.

3.4Data pipeline

3.4.1 Ingestion

FastF1 is the primary telemetry source, with OpenF1 and Ergast as fallbacks for tyre and lap context. Each source sits behind a circuit breaker (5 s timeout, 3 retries with 1–2–4 s backoff, breaker opening after 3 faults in 30 s); an outage serves from the local Parquet telemetry cache tagged STALE_DATA rather than failing. The breaker constants were fixed a priori as conventional operational settings — fail fast within an operator's attention span, outlive a transient network blip but not a real outage — and nothing downstream is sensitive to them, which is why they were never tuned. Telemetry is cached at its raw sample rate, so the resampling policy remains changeable without a re-download.

3.4.2 Validation — nine filters, every loss counted

Every lap passes a chain of nine filters before it may contribute to any statistic. Each filter has its own error code, and each rejection is logged; the acceptance rate is a reported number, not an absorbed one. Of 64,364 laps seen across 2022–2025, 53,972 survived — an 84% acceptance rate dominated by green-flag status and pit events.

Three thresholds deserve their rationale. The 20 Hz floor: the behaviours that distinguish drivers — brake-release shape, throttle ramp rate, brake–throttle overlap — live in transitions of roughly 100–300 ms, and resolving a transition needs several samples inside it; at 20 Hz a 150 ms ramp spans three samples, at 5 Hz it is a single step. The public feed arrives at ≈7.5 Hz, so the corpus is linearly resampled to 50 Hz before validation; this clears the floor mechanically but adds no information, and that honesty is recorded in the matrix metadata and in the limitations (§3.9, Chapter 5) rather than hidden by the resample. The 115% lap-time bound is modelled on the sport's own 107% qualifying rule but set deliberately looser: a race lap at 110% of the driver's session median is usually traffic or tyre management — genuine behaviour worth keeping — while beyond 115% the lap is almost always damage, a cool-down, or an unwound system state that would contaminate a behavioural baseline. The 30-clean-lap floor exists because per-cell statistics (medians, deviations, detector baselines) must be stable against outliers; below roughly 30 samples a single unusual lap visibly moves them. The same floor gates style-space projection for unknown drivers, so every per-cell number in the system rests on the same minimum evidence.

3.4.3 Feature extraction

Each accepted lap yields a fixed 28-feature behavioural vector across six domains — throttle, braking, speed, gear, engine, cornering — plus consistency, corner-balance, and tyre-age drift terms that feed the models but no radar axis. A feature outside its documented physical range is set NULL and logged (FEATURE_001), never clipped silently. Vector assembly tolerates up to six NULLs (≈21% of the vector) via train-median imputation, each imputation tagged IMPUTED; the seventh NULL rejects the lap with LAP_NULL_EXCESS. The ceiling is a designed boundary: every imputed value pulls toward the population median, which by construction erases exactly the individuality the classifier needs, so past six NULLs the vector is more imputation than measurement.

3.4.4 Normalisation — the leakage chokepoint

Six circuit-sensitive features are z-scored per circuit; the rest pass through. The module is deliberately shaped as one writer and two readers: fit_normaliser is the only function in the system that computes normalisation statistics, and the readers (load_normalisation_params, apply_normalisation) are provably free of any fit call — a static scan asserts it. Parameters are persisted to artefacts/normalisation.json, content-hashed, and loaded read-only by training, validation, serving, and upload alike. An unknown circuit falls back to global parameters and logs NORMALISATION_FALLBACK. Figure 3.2 shows the boundary this module defends.

One consequence of this design is recorded here because it shapes the whole results chapter: the per-circuit normalisation assumption was ultimately inverted by evidence for the classifier alone. The ablation study found that the raw levels of the six circuit-sensitive features carry substantial driver-discriminative signal that per-circuit z-scoring erases (held-out macro-F1 0.614 raw against 0.413 normalised on never-trained circuits, so the effect cannot be circuit-identity leakage). The finding was operationalised through a config-recorded decision — the classifier's pipeline serves raw features, its provenance recorded in the model bundle itself — while every other model keeps the leakage-guarded normalised pipeline. The design lesson is stated in §3.9; the implementation of the change in §4.5; the evidence in Chapter 5.

3.5The fingerprint and its models

3.5.1 The fingerprint

Each driver's clean training laps aggregate to a 56-dimensional behavioural distribution — the mean and spread of all 28 features. This is the system's central representation. Identification validates that it carries driver-specific signal; the style space gives it geometry; SHAP explains it; the extended analyses apply it. Everything else in this section is designed around that role.

3.5.2 Identification — the fingerprint's validation

The identification model is an XGBoost multi-class classifier over the 28 behavioural features, isotonic-calibrated on a disjoint 20% split, with hyperparameters selected by a resumable Optuna study. Cross-validation uses StratifiedGroupKFold grouped by circuit, so that an entire circuit sits in one fold: lap-level splitting would let the same circuit appear on both sides of a fold, leaking circuit identity into apparent “driver” performance — the leakage that flatters most published driver-classification numbers. Group CV costs headline score and buys validity; the trade is accepted knowingly.

XGBoost was chosen over its alternatives for three load-bearing properties. The data is tabular — 28 engineered features, ~54,000 rows — which is the regime where gradient-boosted trees remain state of the art. Native NaN handling matches the tolerated-NULL contract with no imputation at serve time; TreeExplainer yields exact SHAP values rather than sampling approximations, which Principle 4 and RQ2 both rely on; and calibrated probabilities make the confidence gate meaningful. Random forests lose the exact explainability and calibrate worse (they are retained as a baseline in Chapter 5); deep and sequence models need more data than four seasons of one series provide and would surrender explainability and reproducibility for uncertain gains (§3.9).

3.5.3 Confidence-aware inference — the licence to abstain

The classifier answers only when it is entitled to. Below the calibrated 0.65 gate the result is LOW_CONFIDENCE; high distribution entropy takes precedence and returns AMBIGUOUS. The gate is only meaningful if “0.65” means what it says: an uncalibrated maximum probability of 0.65 can correspond to a 40% or a 90% empirical hit rate. Isotonic regression was chosen over Platt scaling because it assumes no particular miscalibration shape, and it is fitted on a split the booster never saw. The 0.65 value itself was fixed a priori: for 13 classes it demands 8.5× the chance probability mass before the system will name a driver — post-calibration, roughly “right two times in three” as the minimum standard for a named answer. On the held-out circuits the served system chooses to answer on 71.9% of laps and is right 74.8% of the time when it does, against 63.6% when forced to answer everything: abstention is not a failure mode but the mechanism that turns a hard problem into a trustworthy system.

Following an external design review, every prediction additionally carries a propagated confidence: data completeness × distribution familiarity × calibrated model confidence. Each factor is a distance from a boundary the system already enforces (the NULL ceiling, the ambiguity entropy bound, the calibrated maximum probability), multiplied so that one weak link drags the composite down. The composition introduces no new thresholds, and it explains the gate's verdict without ever overriding it — confidence_state remains authoritative (Principle 4).

3.5.4 Explainability

A TreeExplainer over the champion's base booster produces per-prediction attributions, a global signed-SHAP artefact, and the six-domain signature that drives the interface. Explainability never blocks a prediction: a SHAP fault degrades to SHAP_UNAVAILABLE and the prediction returns without it. The same discipline extends to every other output — deviation alerts ship their exact per-feature attribution, and setup tendencies ship the basis of the heuristic that produced them — so that no served claim is unaccompanied by its provenance.

3.5.5 Style space — the fingerprint's geometry

The 56-dimensional aggregates project by UMAP to a 5D fingerprint coordinate and a 2D view. Unknown drivers project by forward pass — never a retrain — gated for sparsity (SPARSE_PROJECTION below the same 30-clean-lap floor) and out-of-distribution distance (OUT_OF_DISTRIBUTION at Mahalanobis > 3 SD on any principal component). UMAP was chosen because style neighbourhoods are what the space is for, and UMAP preserves local neighbourhood structure through non-linear relationships PCA flattens. But UMAP fitted on 13 points is fragile and non-deterministic across library versions, so a PCA fallback is trained and persisted alongside it: if UMAP cannot serve, the surface degrades to a deterministic projection (UMAP_FALLBACK) instead of dying — the honest-degradation corollary in action. The full chain degrades in order: UMAP → PCA → raw-space nearest-neighbour ranking (PROJECTION_FALLBACK) → a typed refusal (MODEL_NOT_FOUND).

A design review caught that the 56-dimensional aggregate mixed unit-scale fractions with raw physical units spanning four orders of magnitude — a Euclidean UMAP would have measured unit scale, not style — so a train-only aggregate scaler was added inside the leakage guard and recorded as a numbered divergence (§4.11). The episode is reported rather than absorbed because it is the clearest instance of Principle 2's redundancy paying for itself.

3.5.6 Corner decomposition — an ablation instrument

Corners segment into slow, medium, and high-speed classes by apex radius (r = 1/κ at the apex sample), each yielding a five-feature sub-vector (apex speed, lateral g, throttle, brake, steering-reversal rate) aggregated into per-driver sub-fingerprints. Its deliverable is an ablation — does corner-type information improve identification? — designed so that a neutral result is a legitimate finding, not a failure. It deliberately does not retrain the served champion.

3.5.7 Behavioural deviation monitoring

The deviation monitor is deliberately not a learned model, and deliberately not “tyre death prediction”. No labelled degradation events exist to learn from, so a learned model would have nothing defensible to fit; a calibrated statistical detector is explainable and its false-positive rate is derivable. Per lap, the detector computes the cosine distance between the standardised 26-feature behavioural vector (the two tyre-age slope features are excluded — as broadcast columns they would double-count and leak future laps into replay) and a baseline built from the stint's first three clean laps, smooths it with a 3-lap rolling mean, and compares against a threshold τ = μ + 2σ calibrated per driver per circuit type from training data. Two consecutive crossings confirm an alert; a single crossing is a persisted WATCH. The alert payload carries an exact cosine decomposition — per-feature contributions that sum to the score, via 1 − cos θ = ½‖x̂ − b̂‖² — and a pit-window figure stated as what it is: the historical median laps-to-pit for that calibration cell, not a recommendation.

The distance function was chosen against two considered alternatives. Euclidean distance conflates magnitude with shape: fuel burn and track evolution move every feature's magnitude lap by lap, which would read as constant “degradation”. Mahalanobis whitens by a covariance the data cannot support: a 26×26 covariance estimated per 30-lap cell is singular or wildly unstable. Cosine on standardised features isolates exactly the quantity of interest — has the shape of the driver's behaviour rotated away from their own baseline — and is scale-free by construction. The threshold sits two calibrated standard deviations above each cell's own mean deviation: under approximate normality, a ≈2% one-sided per-lap false-positive rate, squared by the two-consecutive-lap confirmation to well under one false alert per thousand scored laps; and because σ comes from the same per-cell calibration as μ, a naturally erratic driver–circuit pairing earns a proportionally wider band instead of a stream of false alerts.

3.5.8 Setup tendency estimation

An exploratory extension, framed as exactly that. APEX estimates telemetry-derived setup tendencies associated with a driver's behavioural fingerprint — heuristic targets, never ground-truth engineering setups, because no public ground-truth setup data exists. The design is three layers: a learned mapping from the 5D fingerprint (concatenated with a drop-first circuit one-hot) to ten setup parameters; an FIA constraint engine (bound clipping, a Monaco maximum-downforce override, consistency warnings); and per-parameter confidence scoring that returns a range rather than a value below the reliability floor (WIDE_CONFIDENCE, ±15%).

The training targets are transparent, monotonic maps of named fingerprint features — a documented heuristic, deliberately without fitted constants, so the learning is confined to the fingerprint→setup mapping. The consequence is a compounding uncertainty the system must not hide, which is why the approximation disclaimer is a required response field, direction language (“less front downforce than the grid reference”) replaces engineering point-values, every tendency names the basis features of its target heuristic, and the specification's own finding — only about five of the ten parameters are reliably inferrable — is reported, never silently narrowed. The extension earns its place through one measured property: the served per-parameter reliability score correlates with held-out error at r = −0.80 — when the system says trust me less, it is measurably less trustworthy.

3.6Serving and interface

The engineering layer supports the system and is not claimed as research. The serving stack is a FastAPI service over PostgreSQL persistence (ten tables covering drivers, sessions, laps, fingerprints, predictions, and the data-quality log), with the inference pipeline resident in process. Three design decisions carry the principles into serving:

  • Best-effort startup, honest health. The application factory loads model handles best-effort in its lifespan: a handle that fails to load degrades to None with a logged reason, and GET /health reports exactly what is unready (503 if and only if the database is down or a handle is missing). A fresh checkout without artefacts serves an honest 503, never a fake 200.
  • /predict never 5xxs on model output and writes nothing. A gated or uncertain prediction is a 200 with a typed state (Principle 4). The endpoint is stateless by design: a live feature-vector POST has no persisted lap identity, and fabricating foreign keys to force a write would violate Principle 1. Persistence of predictions belongs to the batch-ingestion path, which owns real lap identities.
  • Optional infrastructure is actually optional. The Redis cache fronts the expensive endpoints behind its own circuit breaker and is non-critical: the system runs with Redis down. The Celery queue serves batch ingestion; the replay engine re-runs the deviation monitor over a growing prefix of a persisted stint — read-only, deterministic, and causal: lap k uses only laps 1…k, exactly what a live monitor would have known.

The interface is Next.js with a generated, runtime-validated API client returning a four-state result union — loading, empty, error, success — which is Principle 1 reaching the browser. Confidence colour is driven by the served state; no component re-derives a threshold. The palette itself is semantic: assert rose when the model states something, epistemic purple when it declines, operational amber when it serves compromised. Six screens run on the real 2022–2025 corpus — driver overview, driver profile, prediction with setup tendencies, comparison, tyre analysis, and a causal race-replay monitor — and every element whose backing data the API does not serve is rendered as an explicit unavailable state behind a named seam, never fabricated (§4.7).

3.7The failure contract

The failure contract is the design's connective tissue. Sixty-nine typed error codes form an enumeration that is the single vocabulary of failure across the backend, the database, the API surface, and the interface; strings are never hardcoded. The codes partition into data-quality codes (ingestion, validation, features, upload), model lifecycle codes (training, loading, inference), uncertainty states (which are not failures — §3.3), and operational codes (cache, queue, database, API). Every rejected lap, imputed value, fallback, and degraded load writes a row to the append-only data_quality_log, and the interface surfaces the tallies with their reasons verbatim. Two properties make the contract more than a logging convention: every code has a unit test that triggers it (Principle 5), and an executable fault-injection harness (§3.8) demonstrates the seven specification failure scenarios end to end on the assembled system.

3.8Evaluation design

Evaluation is designed into the architecture rather than appended to it; the full protocol and results belong to Chapter 5, but three structural choices are design decisions and are recorded here. First, the held-out-circuit quarantine: Belgium and Italy were excluded from every fitting operation from the first line of code, so the headline identification number is a genuine circuit-generalisation measurement rather than a random-split score. Second, the evaluation framework orchestrates and recomputes nothing: it calls the same read-only surfaces the application serves and harvests the champion training result, with a repository scan asserting it contains no fit call and no metric arithmetic of its own — so the evaluation cannot quietly diverge from the system it evaluates. Third, the failsafe harness is executable: RQ5's evidence is seven fault-injection scenarios (gate behaviour under ambiguity, source outage → stale-cache serving, the NULL-tolerance boundary, the cache forced down across 100 consecutive predictions, database down with no partial write, an out-of-distribution projection, and a raising SHAP explainer) run against the real assembled application, not asserted in prose.

Two further design lessons deserve prose. The per-circuit normalisation inversion (§3.4.4) shows a design assumption — that circuit normalisation removes only nuisance variance — being overturned by the system's own evaluation machinery and then operationalised through a recorded decision rather than a quiet patch: the architecture's willingness to be corrected by evidence is itself a designed property. And the single shared feature pipeline was a deliberate bet: one audited pipeline with per-model feature subsets (the monitor uses 26 of 28; corner decomposition adds its own) was chosen over per-model pipelines because one leakage boundary to defend beats four; the concentration risk is real and is mitigated by the tripwires and per-feature range tests rather than denied.

Chapter 4

Implementation

This chapter describes how the design of Chapter 3 was realised: the specification-driven method, the technology stack and the constraints that shaped it, the implementation of each layer in dependency order, and the quality-assurance regime that gates every merge. It closes with the implementation challenges that most tested the design and the divergence ledger that keeps every departure from the specification reviewable.

4.1Method — specification-driven development

The system was built as twenty-one features in strict dependency order: one feature, one specification, one focused build. Each specification was written and adversarially reviewed before implementation — typically through multi-lens review passes covering fidelity to the master specification, leakage and reproducibility, failure handling, and house conventions — so that design questions were settled on paper where they are cheap to change. Each build ended with a conformance check against the specification's own acceptance criteria and failure-mode table, and merged only with the full test suite, lint, and strict type-checking green. Table 4.1 shows the build order; the layering is the dependency structure of §3.3 made into a schedule.

The automated review gates — an ML-correctness audit (scaler leakage, unseeded randomness, held-out contamination, missing gates), a failure audit (every documented failure mode actually handled, coded, logged, and surfaced), a principles review against the working diff, and a per-feature conformance check — ran on every feature in addition to lint (ruff), strict typing (mypy, tsc), and both test suites. Finally, AI assistance was used throughout the build as an engineering accelerator and is declared per COMP702 policy; the research design, the decisions recorded in these chapters, and the dissertation prose are the author's own.

4.2Technology stack

The backend is Python on FastAPI with Pydantic v2 contracts, SQLAlchemy 2.0 async ORM with Alembic migrations, and Celery for batch work; the ML stack is pandas/numpy (vectorised throughout — no per-row Python loops), XGBoost with scikit-learn's calibration, Optuna for hyperparameter search, umap-learn with a PCA fallback, SHAP for exact tree explanation, and MLflow for run tracking; storage is PostgreSQL and Redis, with Redis explicitly non-critical. The frontend is Next.js 14 (App Router) in strict TypeScript with D3, Three.js (with a D3 2D fallback), Zustand, and Tailwind.

The runtime is Python 3.14, and wheel availability on that platform forced four dependency decisions that were documented as ratified migrations rather than absorbed silently (Table 4.2) — an application of Principle 1 to the build environment itself: every departure has a traceable cause.

scikit-learn's removal of CalibratedClassifierCV(cv="prefit") in the pinned release is handled by wrapping the trained booster in a FrozenEstimator for calibration — a small example of the pattern the whole chapter repeats: platform drift is met with a documented adaptation, never a silent workaround.

4.3Repository organisation

The application is 46 modules in 11 dependency-ordered packages: app/contracts (the error enumeration and typed result objects), app/pipeline (ingest, validate, features, normalise, upload), app/ml (classifier training and inference, explain, style space, corners), app/monitoring (the deviation detector), app/personalisation (the setup engine), app/db, app/api, app/cache, app/tasks, app/replay, and app/eval. The test tree mirrors it — one test module per source module. The per-feature specifications and the index that tracked build order, status, and the divergence ledger were development instruments rather than deliverables; they are preserved in the project's version history and are cited throughout this chapter from there, keeping the working tree to the system itself. A single config.yaml is the source of truth for every constant: 198 keys across 22 typed configuration blocks, each parsed into a Pydantic model with cross-block validators. No threshold lives in code; static scans enforce it.

4.4Pipeline implementation

Contracts first (F00). The error enumeration, the typed result objects, and the configuration loader were built before any pipeline code, so that every later feature had the failure vocabulary available from its first line. Error codes were pre-seeded for features not yet built — the upload codes, the model uncertainty states, the queue codes — which later allowed several features to ship with no new codes, a useful indicator that the failure taxonomy was designed rather than accreted.

Ingestion (F01). The FastF1/OpenF1/Ergast clients sit behind the §3.4.1 circuit breaker, implemented once and reused; raw telemetry is persisted to a Parquet cache at source sample rate. Per-lap track status was added to the cache schema and the F01→F02 column contract as an additive amendment when validation needed it — the first exercise of the amendment discipline that governed all later contract changes.

Validation (F02). The nine-filter chain of Table 3.1 is a pure function over the session frame returning a typed ValidationResult; review hardening added two codes beyond the specification (ORPHAN_SAMPLES for samples whose lap is null, and VALIDATION_ERROR as the malformed-frame backstop, kept distinct from per-lap data codes).

Feature extraction (F03a/F03b). The 28-feature extraction was split into the 22 scalar-channel features plus the shared vector contract (F03a), and the X/Y-positional cornering features, corner balance, and tyre-age slopes (F03b) which plug into the same vector without changing it. The NULL contract of §3.4.3 — catch, mark NULL, log, continue; reject past six — lives in F03a's assembly and is exercised by both suites.

Normalisation (F04). The one-writer/two-reader module of §3.4.4 shipped as machinery before any training matrix existed; the first real artefacts/normalisation.json materialised with the first classifier training. The per-circuit fit floor reuses the global 30-clean-lap threshold, applied per circuit — a documented decision rather than a new constant.

Manual upload (F05). The CSV upload endpoint runs the real F02 validator and F03 extraction behind eight specified edge-case handlers (missing columns, suspected-unit errors, corrupt rows, emptiness, and friends — UPLOAD_001–004 plus tags). It is synchronous and stateless, mirroring /predict: the response is the cleaning report, and nothing is written. Imputation uses injected train-only feature medians, with a leakage scan asserting no fit and no median computed on upload data (Principle 2 extended to user-supplied data). Denial-of-service guards cap file size and row count before parsing.

4.5Model implementation

The classifier and the champion-bundle seam (F06a/F06b). The classifier was split into training and inference features whose only interface is the registered champion bundle (Figure 4.1): training produces classifier.pkl, normalisation.json, labels.json, and a bundle_meta.json provenance sidecar; inference loads them read-only, cross-checks the label map against the champion's class count, and refuses to serve (MODEL_NOT_FOUND) on any mismatch — fail-loud, never fail-quiet. Training runs a resumable Optuna study (200-trial floor, ≈3.3 minutes per trial, ≈11 hours wall) with relational-database storage, so a crash resumes rather than restarts — a property exercised in anger when the raw-representation study was resumed from trial 31 after an interruption. Isotonic calibration is fitted on a disjoint 20% split the booster never saw, and every run is logged to MLflow with parameters, metrics, and artefacts.

The seam earned its keep twice. First, when integer-fitted class labels left the index→driver map unavailable at serving, the fix was an additive artefact (labels.json) plus a load-time cross-check, not a shared import. Second, when the representation finding of §3.4.4 was operationalised, the change was confined to training — use_circuit_normalisation: false, a fresh Optuna study on the raw space, a re-registered champion — while serving obeys the bundle: the sidecar records the representation, legacy bundles without a sidecar serve normalised, and a corrupt sidecar refuses to serve. The served champion's held-out macro-F1 rose from 0.4068 to 0.6225; the run still reports DEGRADED against its 0.78 a-priori target, exactly as designed.

Explainability (F07). The explainer unwraps the calibration wrapper to reach the champion's base booster and runs TreeExplainer in exact mode, filling the prediction result's SHAP fields, a global signed-SHAP artefact, and the multi-season Jensen–Shannon stability measure. Review hardening pinned the class-order mapping to the explainer's own driver list and guarded the all-NaN season case — small fixes, each with a regression test.

Style space (F08). The build fits UMAP and the PCA fallback inside the leakage guard and persists both, with a cross-bundle fingerprint (the scaler's hash recorded in the UMAP bundle) so mismatched artefacts refuse to co-serve. The Gate-2 review before merge caught the aggregate-scale defect of §3.5.5; the fix — a train-only aggregate StandardScaler applied at a single projection chokepoint — was recorded as divergence #6 and flagged to the supervisor, since the master specification is silent on aggregate scale. The degrade chain (UMAP → PCA → raw-space nearest neighbours → typed refusal) is fully test-covered, including the load-time dimension checks that catch a stale bundle.

Corner decomposition (F09). Implementation refined the apex-radius estimate to the curvature at the speed-minimum sample (robust to the boundary artefacts that dominate a window maximum) and established that the five corner sub-features are new derived quantities the normaliser never scaled — so F09 is normalisation-free by construction (divergence #23), scoring its ablation through scale-invariant XGBoost. Thin cells surface DEGRADED with DATA_INSUFFICIENT rather than being padded.

Deviation detector (F10). Calibration and serving share one pure scoring core, giving parity by construction: the τ table is calibrated by the same code path that scores live laps. Calibration is train-only and tripwired, its artefact content-hashed and timestamp-free; loading refuses on schema, hash, or width mismatches. A structural-versus- crossing distinction governs configuration drift: a changed structural knob refuses to load, while a changed crossing knob only invalidates the pit-window claim. The 26-dimension standardiser of §3.5.7 lives inside the calibration artefact — the same single-writer pattern as normalisation, applied one level down.

Setup engine (F11). Ten per-parameter XGBoost regressors over the 5D fingerprint with a drop-first circuit one-hot; the constraint layer applies FIA clipping (CONSTRAINT_CLIPPED), the Monaco override (CIRCUIT_OVERRIDE_MONACO), and consistency warnings; the confidence layer computes per-parameter reliability as 1 − CV-nRMSE, attenuated for out-of-distribution queries and never NULL. The external design review later added the grid-reference tendency phrasing and the served basis-features field (§3.5.8) as additive contract changes.

4.6Platform implementation

Persistence (F12). The ten-table schema is SQLAlchemy 2.0 async ORM with Alembic migrations. Portable column types (with_variant: native JSONB/ENUM/UUID on PostgreSQL, JSON/checked-VARCHAR on SQLite) let the entire DB suite run offline on aiosqlite, with a marked test exercising the real migration round-trip against PostgreSQL when a DSN is provided. The database sits behind its own async circuit breaker (DB_UNAVAILABLE), the health probe never raises, the data_quality_log gains its PostgreSQL sink here, and the DSN is environment-only — configuration stores the variable's name, never a secret.

API surface (F13). The FastAPI application factory wires the never-raising model handles and the persistence seam into the REST surface: ten synchronous endpoints implemented in full, and the four asynchronous/upload/replay routes shipped as honest 503 stubs with real schemas until their engines existed — visible incompleteness rather than a fake implementation. Handles are dependency-injected and loaded best-effort in the lifespan (§3.6); endpoint tests inject fakes through the DI seam. A failure audit on the API layer confirmed the serving invariants — /predict never 5xxs on model output, no partial writes, rollback before raise, no stack-trace leakage — and its findings (a spoofable metrics-endpoint header check among them) were fixed with regression tests.

Cache, queue, and replay (F14). The Redis cache is cache-aside behind its own breaker and never raises: a cache fault logs and falls through to computation (CACHE_UNAVAILABLE is a tag, not an outage). Batch ingestion is a Celery task that atomically persists laps, predictions, and fingerprints — this path, which owns real lap identities, is the writer that the stateless /predict deliberately is not. The replay engine re-runs the deviation monitor over a growing prefix of a persisted stint, read-only and causal. The test suite runs offline on fakeredis and eager Celery, with marked tests gating the real infrastructure.

The fault-injection harness (F15). The harness assembles the real application — real wiring, injected faults — and executes the seven §3.8 scenarios, producing a content-hashed results table consumed by the evaluation framework. Its own review hardening mattered: the harness was redirected to temporary stores so that running the failsafe suite can never pollute the operational cache or data-quality log, and it survives a scenario that raises during setup — the failure harness itself obeys the failure contract.

4.7Frontend implementation

The frontend began with the design system and the API client (F16a): design tokens; loading states as telemetry-wave skeletons, never spinners; error cards carrying the monospace error code and a retry; and a client whose TypeScript types and error-code union are generated from a committed OpenAPI snapshot, validated at runtime with zod, and guarded by a backend test that fails if the snapshot drifts from the live schema. Every fetch returns the four-state result union of §3.6, and the only frontend-local codes are the pre-API failures (UI_NETWORK, UI_TIMEOUT, UI_SCHEMA_MISMATCH).

The screens were then built in dependency order (F16b–F19), and the build's most consistent pattern deserves its name: the honesty landmine. At each screen, some specified UI elements had no backing endpoint — a compatibility score, per-lap SHAP, corner sub-fingerprints, the replay threshold and alert payload, a session catalog. Each was either derived honestly from what the API does serve (and labelled as a proxy), or rendered as an explicit unavailable state behind a named seam in the DTO — never fabricated. Later redesign cycles closed the major seams by widening the DTOs with data the models had computed all along: the replay endpoint gained the per-lap threshold and the full alert payload, a session catalog replaced raw-UUID entry, and the comparison screen gained true per-feature signed-SHAP deltas. One real display bug was found and fixed in the process: comparison radars clamped unbounded SHAP magnitudes to a unit radial, so most axes rim-clamped into near-identical shapes; the redesign scales both radars and the delta by one shared per-axis maximum, stated in an on-screen caption.

The frontend embodies the principles rather than merely consuming them: confidence colour comes only from the served state, deterministic seeded layouts keep charts reproducible, and 271 component tests exercise every screen behaviour and every failure state — the no-fabrication tests assert that a missing endpoint renders an unavailable state rather than an invented number.

4.8Evaluation framework

The evaluation framework (F20) implements the §3.8 design: one async orchestrator over the four evaluation pillars plus the corner ablation, calling only the system's read-only surfaces and harvesting the champion's training result. A repository-scan test asserts it contains no fit call and no metric arithmetic beyond value-versus-target comparison. It never raises — a pillar fault degrades to a skipped pillar with a finding — and its report is content-hashed over outcomes and verdicts, mirroring the failsafe report. Offline, the framework still runs as a mechanism (the failsafe pillar executes; the data pillars skip with reasons); the real-corpus numbers are produced by artefact-gated tests that skip in the absence of the committed champion and matrices. A held-out gate added in review ensures the generalisation evaluators score on the held-out slice only — and skip with a reason rather than silently scoring on training data.

4.9Quality assurance

The quality regime is the implementation's answer to Principle 5, and it is measurable (Table 4.3). The backend suite mirrors the application tree with synthetic passing and failing fixtures; every error code has a triggering test; the suites run fully offline by design — aiosqlite for the database, fakeredis and eager Celery for infrastructure, injected fakes for model handles — with marked test tiers (artefacts, postgres, redis, celery) gating everything that needs real artefacts or services. Static scans enforce the structural rules: no fit calls outside the four tripwired sites, no magic numbers outside configuration, no hardcoded error strings. The OpenAPI drift guard ties the generated frontend client to the live backend schema, so a contract change that forgets the frontend fails a backend test.

4.10Implementation challenges

The representation inversion. The build's largest course-correction began as an evaluation anomaly: cross-validation plateaued far below target on the real corpus, and the ablation matrix then showed the identical model scoring 0.614 on raw features against 0.413 normalised on the held-out circuits. Because the held-out circuits were never trained on, the explanation could not be leakage; per-circuit z-scoring was erasing driver signal, and a secondary effect (held-out circuits falling to the global-fallback statistics) accounted for only a minority of the gap — a paired calibration study bounded that part at roughly three F1 points. Turning the finding into the served system exercised every discipline this chapter describes: a config-recorded decision, a fresh resumable study, provenance in the bundle, serving that obeys the bundle, and an in-training counterfactual (the normalised road scores 0.449 from inside the same run) confirming the inversion. The design assumption, its overturning, and the operationalisation are all in the record.

Small-sample geometry. UMAP fitted on 13 aggregate points is at the edge of the method's validity, and it is stochastic: coordinates are reproducible within tolerance under a fixed seed, but the persisted model is not byte-identical. The implementation answers with the persisted deterministic PCA fallback, a measured stability protocol, and — from the aggregate- scale episode — a healthy scepticism that was subsequently encoded as load-time dimension and provenance checks on every bundle.

The platform itself. Building on a leading-edge Python meant wheel availability drove four stack migrations (§4.2). The discipline that contained the risk was always the same: re-run the full existing suite green on the new pin before writing any new feature code, and record the migration with its cause.

Keeping an offline-honest suite. A test suite that needs live services or committed model artefacts stops being run. Nearly every subsystem therefore has an offline mechanism tier and a gated real tier; the discipline surfaced real bugs — among them a .gitignore pattern that silently swallowed an entire source package from a clean checkout, caught only because a clean-checkout import was part of the offline gate.

4.11The divergence ledger

Seventy-eight numbered divergences record every place the implementation departs from the master specification, each with its reason and its supervisor-visibility. They are not errata: several are the most defensible decisions in the project — the aggregate scaler (divergence #6), the stateless /predict (#30), the normalisation-free corner ablation (#23), the raw-representation champion. Others record honest deferrals later closed (the replay payload seams) or genuine specification gaps (an inverted unit-detection threshold copied verbatim and flagged rather than silently corrected). The ledger's purpose is methodological: a specification-driven build is only trustworthy if departures from the specification are as reviewable as conformance to it. Recording them is what makes the departures reviewable rather than invisible — Principle 1, applied to the process that built the system that enforces it.
