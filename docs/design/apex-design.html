01

Problem and hypotheses

Two drivers in mechanically identical cars produce measurably different telemetry. APEX treats that difference as a behavioural signature and asks what it supports: identification, placement in a continuous style space, live deviation detection, and translation into car-setup direction. The system is deliberately not a single model — it is a pipeline whose contracts are the engineering content, and the research questions are answered as much by what the system refuses to do as by what it outputs.

Each research question is held to a measurable hypothesis. Where a target was fixed a priori in the specification and the observation landed elsewhere, both numbers appear — the reading is argued in §10, never silently rebased.

02

Novelty and contributions

The novelty is not XGBoost, SHAP, UMAP or FastAPI — those are commodity components. The contribution is the fail-safe behavioural pipeline they sit inside: a telemetry-to-recommendation system in which every failure path is typed, every model output carries a gated confidence, every departure from specification is a numbered, reviewable decision, and the interface renders uncertainty instead of hiding it. Published driver-classification work rarely ships confidence gating, typed uncertainty, or a production failure contract at all; APEX makes those the core of the design (the comparison matrix is in §8).

Research contributions

  • A 28-feature behavioural fingerprint from public telemetry, with a measured account of what the public feed can and cannot support
  • Confidence-aware driver identification: gated predictions with typed uncertainty states and a propagated confidence composition
  • A continuous driver style space with an honest small-sample treatment and a deterministic fallback
  • Statistical (deliberately non-learned) degradation detection with per-driver calibrated thresholds and exact attribution
  • Style-conditioned setup tendencies under explicit approximation disclaimers
  • The held-out-circuit evaluation design and its structural findings (§10)

Engineering achievements

  • The failure contract: 69 typed error codes, an append-only data-quality log, and an executable fault-injection harness
  • Leakage-proof normalisation with tripwires at every fit site
  • Byte-reproducible training runs (fixed seeds, content-hashed artefacts, MLflow)
  • A typed API surface with a generated client, runtime validation, and drift guards
  • Six live screens on real data, every unavailable element rendered honestly
  • Circuit breakers, cache-optional serving, offline-capable persistence tests

These two columns are kept distinct on purpose: implementation effort is not claimed as academic novelty, and the research claims do not borrow weight from the tooling.

03

Design principles

Five constraints were fixed before any code and are enforced mechanically rather than by convention. They are defined once, here; the rest of the document refers to them by number rather than re-explaining them.

1 · No silent failure

Every failure path returns a typed result carrying an explicit error code. No bare except, no dropped lap, no swallowed fault.

Enforced by: 69-member ErrorCode enum · append-only data_quality_log · a read-only failsafe-auditor run per module
2 · No normalisation leakage

Scalers are fitted on the training split only, persisted, and loaded for everything downstream. Belgium and Italy never touch a .fit() call.

Enforced by: single-writer/two-reader normalisation · _assert_no_leakage tripwires at four fit sites · ml-auditor
3 · Reproducibility

All seeds fixed in config.yaml. Artefacts are content-hashed and timestamp-free so a re-run is byte-identical.

Enforced by: seeds 42 · n_jobs=1 pinned in XGBoost · MLflow run per training · deterministic artefact hashing
4 · Mandatory confidence gates

Model output below threshold returns an uncertainty state, never a forced answer.

Enforced by: LOW_CONFIDENCE / AMBIGUOUS / OUT_OF_DISTRIBUTION · gate at max-prob < 0.65 · UI colours read the state, never re-derive it
5 · Failure paths are unit-tested

Every error code has a test that triggers it. A feature is not done because the happy path works.

Enforced by: 50 test modules mirroring app/ · synthetic passing and failing fixtures · /spec-check before DONE
Corollary · Honest degradation

Where a component cannot deliver, it says so in the type system rather than substituting a plausible value.

Consequence: DEGRADED is a first-class status, and the UI renders explicit unavailable states rather than fabricating.

Why this dominates the design

Principle 2 makes normalisation a chokepoint every downstream model must pass through, which is why the classifier, style space, detector and setup engine each re-derive and re-assert the train/held-out boundary independently rather than trusting their caller. That redundancy is deliberate: a single filter bug cannot silently poison an artefact.

05

Data pipeline

Ingestion

FastF1 is the primary telemetry source, with OpenF1 and Ergast as fallbacks for tyre and lap context. Each source sits behind a circuit breaker; an outage serves from the local Parquet cache tagged STALE_DATA rather than failing, and telemetry is cached at its raw sample rate so the resampling policy stays changeable without a re-download.

Why 5 s timeout · 3 retries · 1-2-4 s backoff · breaker at 3 faults/30 s

Fail fast within an operator's attention span rather than hang: 5 s bounds a single attempt, three retries with doubling backoff (≈7 s spread) outlive a transient network blip but not a real outage, and the breaker stops hammering a source that has failed three times in half a minute — at which point the cache path takes over. The values were fixed a priori in the specification as conventional operational settings; nothing downstream is sensitive to them, which is why they were never tuned.

Of 64,364 laps seen in 2022–2025, 53,972 survived — an 84% acceptance rate, dominated by green-flag status and pit events, and reported rather than absorbed.

Why a 20 Hz floor

The behaviours that distinguish drivers — brake release shape, throttle ramp rate, brake-throttle overlap — live in transitions of roughly 100–300 ms. Resolving a transition needs several samples inside it; at 20 Hz a 150 ms ramp spans three samples, at 5 Hz it is a single step. The public feed arrives at ≈7.5 Hz, so the corpus is linearly resampled to 50 Hz before validation: this clears the floor mechanically but adds no information, and that honesty is recorded in the matrix metadata and §12 rather than hidden by the resample.

Why a 115% lap-time bound

Modelled on the sport's own 107% qualifying rule but set deliberately looser: a race lap at 110% of the driver's session median is usually traffic or tyre management — genuine behaviour worth keeping — while beyond 115% the lap is almost always damage, a cool-down, or an unwound system state that would contaminate a behavioural baseline.

Why 30 clean laps per driver-circuit pair

Per-cell statistics (medians, deviations, detector baselines) must be stable against outliers; below roughly 30 samples a single unusual lap visibly moves them. The same floor gates style-space projection for unknown drivers, so every per-cell number in the system rests on the same minimum evidence.

Feature extraction

Each accepted lap yields a fixed 28-feature behavioural vector across six domains — throttle, braking, speed, gear, engine, cornering — plus consistency, corner-balance and tyre-age drift terms that feed the models but no radar axis. A feature outside its documented range is set NULL and logged, never clipped silently.

Why a 6-NULL ceiling

Vector assembly tolerates up to six NULLs (≈21% of the vector) via train-median imputation, each tagged. Past that point the vector is more imputation than measurement: every imputed value pulls toward the population median, which by construction erases exactly the individuality the classifier needs. The seventh NULL therefore rejects the lap with a code rather than serving a hollowed-out vector.

Normalisation — the leakage chokepoint

Six circuit-sensitive features are z-scored per circuit; the rest pass through. The module is one writer and two readers: fit_normaliser is the only function that computes statistics, and the readers are provably free of any fit call. An unknown circuit falls back to global parameters and logs the fallback — a fact that §10 shows matters considerably.

06

The four models

Driver identification

An XGBoost multi-class classifier over the 28 normalised features, isotonic-calibrated on a disjoint 20% split, hyperparameters from a 201-trial resumable Optuna study. Cross-validation is StratifiedGroupKFold grouped by circuit, so an entire circuit sits in one fold — lap-level splitting would let the same circuit appear on both sides, which is the leakage that flatters most published numbers.

Why XGBoost over the alternatives

The data is tabular — 28 engineered features, 54k rows — which is the regime where gradient-boosted trees remain state of the art. Three properties clinched it over the candidates: native NaN handling matches the tolerated-NULL contract with no imputation at serve time; TreeExplainer gives exact SHAP values rather than sampling approximations; and calibrated probabilities make the confidence gate meaningful. Random forests lose the exact-explainability and calibrate worse (§8); deep models need more data than four seasons provide and would surrender explainability — a trade examined further in §11.

Why isotonic calibration, and why the gate sits at 0.65

The gate is only meaningful if "0.65" means what it says: an uncalibrated max-prob of 0.65 can correspond to a 40% or a 90% empirical hit rate. Isotonic regression was chosen over Platt scaling because it assumes no particular miscalibration shape, and it is fitted on a split the booster never saw. The 0.65 value itself was fixed a priori: for 13 classes it demands 8.5× the chance probability mass before the system will name a driver — post-calibration, roughly "right two times in three" as the minimum standard for a named answer. Below it the result is LOW_CONFIDENCE; high distribution entropy takes precedence and returns AMBIGUOUS.

Since the supervisor review, every prediction also carries a propagated confidence: data completeness × distribution familiarity × calibrated model confidence, each factor a distance from a boundary the system already enforces, multiplied so one weak link drags the composite down. It introduces no new thresholds, and it explains the gate's verdict without ever overriding it (principle 4).

Explainability

A TreeExplainer over the champion's base booster produces per-prediction attributions, a global signed-SHAP artefact, and the six-domain signature that drives the interface. Explainability never blocks a prediction: a SHAP fault degrades to SHAP_UNAVAILABLE and the prediction returns without it. The same discipline now extends to the other outputs: degradation alerts ship their exact per-feature attribution, and setup tendencies ship the basis of the heuristic that produced them.

Style space

Each driver's clean training laps aggregate to a 56-dimensional distribution — mean and spread of all 28 features — projected by UMAP to a 5D fingerprint and a 2D view. Unknown drivers project by forward pass, never retraining, gated for sparsity and out-of-distribution distance.

Why UMAP, why a PCA fallback, and why the aggregate scaler exists

Style neighbourhoods are what the space is for, and UMAP preserves local neighbourhood structure through non-linear relationships PCA flattens. But UMAP on 13 points is fragile and non-deterministic across library versions, so a PCA fallback is trained and persisted alongside it: if UMAP cannot serve, the surface degrades to a deterministic projection instead of dying (the honest-degradation corollary). A review also caught that the 56-dim aggregate mixed unit-scale fractions with raw physical units spanning four orders of magnitude — Euclidean UMAP would have measured unit scale, not style — so a train-only aggregate scaler was added inside the leakage guard, recorded as numbered divergence #6.

Degradation detection

Deliberately not a learned model. Per lap: the cosine distance between the standardised behavioural vector and a baseline from the stint's first three clean laps, a 3-lap rolling mean, and a comparison against τ = μ + 2σ calibrated per driver per circuit type from training data. Two consecutive crossings confirm an alert; one is a persisted WATCH. The alert payload carries an exact cosine decomposition — per-feature contributions that sum to the score — not an approximation.

Why cosine distance, and why τ = μ + 2σ

Three distance functions were considered. Euclidean conflates magnitude with shape — fuel burn and track evolution move every feature's magnitude lap by lap, which would read as constant "degradation". Mahalanobis whitens by a covariance the data cannot support: a 26×26 covariance estimated per 30-lap cell is singular or wildly unstable. Cosine on standardised features isolates exactly the quantity of interest — has the shape of the driver's behaviour rotated away from their own baseline — and is scale-free by construction. The threshold sits two calibrated standard deviations above each cell's own mean deviation: under approximate normality a ≈2% one-sided false-positive rate per lap, squared by the two-consecutive-lap confirmation to well under one false alert per thousand scored laps. σ comes from the same per-cell calibration as μ, so a naturally erratic driver-circuit pairing earns a proportionally wider band instead of a stream of false alerts.

Setup tendencies

Reframed since the supervisor review from "setup prediction" to what the evidence supports: tendency estimation. Three layers — a learned mapping from the 5D fingerprint to ten setup parameters, an FIA constraint engine, and per-parameter confidence scoring that returns a range below the reliability floor. Every recommendation now states its direction against a grid reference computed from the model's own outputs ("less front downforce than the grid average"), names the basis features of its target heuristic, and ships under a mandatory approximation disclaimer. The specification's own finding — only about five of ten parameters are reliably inferrable — is reported, not narrowed.

Why the targets are heuristic, and why that is stated everywhere

No public ground-truth setup data exists. The training targets are transparent, monotonic maps of named fingerprint features — a documented heuristic, deliberately without fitted constants, so the learning is confined to the fingerprint→setup mapping. The consequence is a compounding uncertainty the system must not hide, which is why the disclaimer is a required response field, the direction language replaces engineering point-values, and the per-parameter SHAP over opaque projection axes is never translated into driving-trait prose it cannot support.

Corner decomposition

Corners segment into slow / medium / high-speed by apex radius, each with a five-feature sub-vector. Its deliverable is an ablation — does corner-type information improve identification? — where a neutral result is a legitimate finding.

07

Platform and interface

Persistence is ten async SQLAlchemy tables with portable column types, so the entire database suite runs offline on SQLite while a marked test exercises the real Postgres migration. The API is a FastAPI factory with a best-effort lifespan: model handles that fail to load degrade to None with a logged reason, /health reports exactly what is unready, and the cache is explicitly non-critical — Redis down costs latency, never availability. Batch ingestion runs through Celery; the replay engine re-runs the detector over a growing prefix of a persisted stint, read-only and deterministic.

The interface is Next.js 14 with a generated, zod-validated API client returning a four-state result union — loading, empty, error, success — which is principle 1 reaching the browser. Confidence colour is driven by the served state; no component re-derives a threshold. All six screens were rebuilt against the design reference during this review cycle and run on the real 2022–2025 corpus:

Earlier iterations deferred UI elements whose data the API did not yet serve, each behind a named seam rather than a fabrication. The remaining deferrals are listed in §12; none are silent.

Trade-offs — the roads not taken

Every load-bearing choice had a considered alternative. The ones that shaped the system:

AlternativeRejected because
Random forest classifierWeaker probability calibration and no exact SHAP — both load-bearing for principles 4 and RQ2. Kept as a baseline, where APEX beats it 1.7×.
Deep / sequence modelsFour seasons of one series is small data; end-to-end representation learning would surrender exact explainability and reproducibility for uncertain gains. Revisited honestly in §11.
Learned degradation modelNo labelled degradation events exist to learn from. A calibrated statistical detector is defensible, explainable, and its false-positive rate is derivable.
One monolithic pipelineFailure isolation becomes impossible — one exception tears down unrelated capability. Five layers with typed boundaries let each fail alone.
Hidden failure recoverySilently retrying or substituting defaults violates principle 1: a masked fault reappears as an unexplainable result. Every recovery is coded and logged.
Lap-level cross-validationThe same circuit on both sides of a fold leaks circuit identity into "driver" performance. Group-by-circuit CV costs headline score and buys validity.
asyncpg · full MLflow · pandas 2Wheel availability on the pinned Python forced psycopg v3, mlflow-skinny and the pandas 3 / numpy 2 line — each migration ratified and recorded, not absorbed.
CVAE performance predictor (original plan)Removed at specification stage, before any code: the Failsafe Edition's §13 replanning note records "CVAE removed (saves 3 weeks)", with the freed weeks redistributed to hardening, failsafe testing and evaluation — the work that became RQ5's strength. Performance prediction survives only in its measured, non-generative form: the fuel-corrected tyre-wear curves.

Failure recovery, executed

The fault-injection harness assembles the real application and injects seven faults — gate behaviour, source outage → stale-cache serving, the NULL-tolerance boundary, Redis down across 100 consecutive predictions, database down with no partial write, an out-of-distribution upload, and a raising SHAP explainer. All seven resolve to coded, logged, served outcomes; none reach a bare exception. This is RQ5's evidence, and it is executable rather than asserted.

A six-fold spread from LEC (0.68) to STR (0.11): some drivers are far more identifiable from behaviour alone. Whether that reflects genuine distinctiveness, unequal lap counts or teammate confusion needs the confusion-matrix analysis in the evaluation chapter.

A structural finding, not a bug

The training run's data-quality log contains 3,946 NORMALISATION_FALLBACK rows — exactly the size of the test split. Every held-out lap normalised through the global fallback, because genuinely unseen circuits have no per-circuit statistics (principle 2 working as specified, and logged). The headline is therefore measured under globally-normalised features while cross-validation was not — a structural contributor to the 0.483 → 0.407 drop that belongs in the evaluation chapter's method discussion, quantified, rather than patched.

What DEGRADED means here

The classifier missed its target and reported so — the run records the miss and writes the champion rather than forcing a pass. The 0.78 target was calibrated against a synthetic fixture; 13-way identification on public telemetry — boolean brake channel, 7.5 Hz true rate — is a substantially harder problem. The honest reading: the signal is real (5.3× chance, 1.7× the strongest baseline) and weaker than the target assumed, and the constraint analysis belongs to the data, not the architecture.

The normalisation inversion — this cycle's strongest finding

Training the identical model on raw features lifts held-out macro-F1 from 0.413 to 0.614. Belgium and Italy were never trained on, so this cannot be circuit-identity leakage: the raw levels of the six circuit-sensitive features carry substantial driver-discriminative signal that per-circuit z-scoring erases — and the zero-shot fallback mismatch (worth only ~3 points, per Evaluation B) is the smaller part of the cost. The hyperparameters were tuned on normalised features, so 0.614 is a lower bound on the raw representation's ceiling.

The specification's assumption that circuit normalisation removes only nuisance variance is, on this corpus, inverted — and the finding was operationalised the same day: the classifier (alone) was re-scoped to the raw representation via a config-recorded decision, its Optuna study re-run from scratch on the raw feature space (a fresh study by construction — the study key hashes the fit data), and the champion re-registered as model v2. Served held-out macro-F1: 0.6225 (counterfactual normalised road: 0.449, confirming the inversion from inside training). Per-driver: LEC 0.85, VER 0.72, ALB 0.72 … worst now HUL 0.47 — STR rose from 0.11 to 0.55. The bundle records its representation and serving obeys the bundle; every other model keeps the leakage-guarded normalised pipeline unchanged. The 0.78 target remains unmet and the run reports DEGRADED, exactly as designed.

The supervisor review raised twelve system-level critiques. Three were implemented in this cycle; the rest are answered here — some defended, some accepted as the strongest future directions. None are ignored.

CritiqueResponseDetail
Setup prediction over-claims implemented Reframed as tendencies: direction vs a grid reference from the model's own outputs, no reference → no direction, disclaimer mandatory.
No uncertainty propagation implemented The propagated-confidence composition on every prediction — three served signals multiplied, zero new thresholds, gate untouched.
Only predictions are explained implemented Degradation alerts ship exact per-feature attribution; setup tendencies ship their heuristic basis. Style-cluster explanation remains open.
Driver ID is the weakest primary objective reframed Accepted in part: the fingerprint is the system's real intermediate representation — identification is its validation (if identity isn't recoverable, the fingerprint carries no signal), and comparison, deviation and setup are its applications. The dissertation frames it this way.
Everything rides one feature pipeline defended A single audited pipeline with per-model feature subsets (the detector uses 26 of 28; corner decomposition adds its own) was chosen over per-model pipelines: one leakage boundary to defend beats four. The risk is real and is mitigated by the tripwires and per-feature range tests.
Models don't communicate partial The detector consumes the style-space projection per lap (the replay's fingerprint drift); setup consumes the fingerprint. Deeper coupling — e.g. personalisation reading classifier uncertainty — is future work.
Style space loses temporal information future work True by construction: mean/spread aggregation discards sequence. Sequence embeddings or a temporal encoder are the natural successor — with the honest cost of losing exact explainability and small-data reliability.
Features are static / no learned representation future work A hybrid (28 engineered + learned latent features) is the credible next architecture; four seasons of one series is at the edge of what representation learning rewards.
No what-if simulation future work The strongest proposed application: perturb a behavioural feature, project the fingerprint shift, re-gate the prediction. The serving surfaces exist; the missing piece is a validated perturbation model rather than plumbing.
No graph representation future work Corners, sectors, laps and drivers do form a graph. A GNN treatment is a research programme in its own right, out of scope for this build.
No ensemble disagreement signal future work Model disagreement as an uncertainty input is compatible with the propagated-confidence design — a fourth factor — and is the cheapest of the future items.
"Replace the architecture with a temporal encoder → embedding hub" defended The proposed shape — one latent representation feeding every head — is already APEX's shape, with an engineered fingerprint as the embedding. Swapping it for a learned temporal one is the future-work column above, not a rebuild: the contracts, gates, and serving layer survive unchanged.

How it was built

One feature, one specification, one focused session. Each specification is written and adversarially reviewed before implementation; each build ends with a conformance check against its own acceptance criteria and failure-mode table, and merges only with the full suite green.

The divergence ledger

Seventy-eight numbered divergences record every place the implementation departs from the master specification, with the reason. They are not errata — several are the most defensible decisions in the project (the aggregate scaler, the 28-feature champion, the stateless /predict). Recording them is what makes the departures reviewable rather than invisible, and this review cycle closed several by widening the API rather than amending the ledger.

Ratified stack migrations

Four dependency decisions changed the stack mid-build and were documented rather than absorbed: pandas 3 / numpy 2 on modern Python (forced by wheel availability), mlflow-skinny because full MLflow caps pandas below 3, SHAP pulling numpy back a minor version, and psycopg v3 where asyncpg ships no compatible wheel. Each is recorded in the project constitution so downstream behaviour has a traceable cause.
